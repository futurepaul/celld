# V8

celld runs untrusted Worker code in V8, so a V8 bug is a bug in celld's
isolation. This fork links its own build of V8, patched to the newest fix
Chrome shipped on that V8 branch, rather than the prebuilt archive denoland
publishes with each `v8` crate release. Those releases go weeks without a V8
patch: `v8` 152.2.0 shipped V8 15.2.124.1 on 2026-08-20, and Chrome then
shipped 43 more 15.2 patches, among them the fix for CVE-2026-85046 (a V8
type confusion exploited in the wild, fixed in Chrome 152.0.7977.82 with
V8 15.2.124.21).

## What celld links

`.cargo/config.toml` pins it, and every value there is forced over the
environment:

| Variable | Meaning |
| --- | --- |
| `CELLD_V8_VERSION` | The V8 version. celld refuses to compile without it. At V8 startup it asserts that the linked V8 reports this version (with rusty_v8's `-rusty` suffix), and a test checks the same. `celld --version` prints what the linked V8 reports. |
| `RUSTY_V8_ARCHIVE` | Where the `v8` crate's build script fetches the static library: a release asset on this repository. |
| `RUSTY_V8_ARCHIVE_SHA256` | The archive's SHA-256. The build script checks it before using the archive, and fails on a mismatch. |
| `CELLD_V8_BINDING_SHA256` | The SHA-256 of the crate's own Rust binding for the target, as the `.crate` that Cargo.lock checks holds it. celld's build script checks the binding the `v8` crate compiles against it. |
| `RUSTY_V8_SKIP_DOWNLOAD` | Forced off, so the archive is always fetched and checked. |

The Rust binding celld compiles is the one the `v8` crate ships. The `v8`
build script also honors variables that bring other V8 code in without a
check: `RUSTY_V8_MIRROR`, `RUSTY_V8_SRC_BINDING_URL` and
`RUSTY_V8_SRC_BINDING_PATH` replace the binding (Rust source, compiled into
celld) with an unhashed file, `DENO_TRYBUILD` skips the archive and its hash,
`V8_FROM_SOURCE` builds V8 from the crate's sources, and `V8_FORCE_DEBUG`
selects another binding and archive. celld's own build script
(`crates/celld/build.rs`) fails the build when any of them is set, to any
value, and for a target the pinned archive is not for, and without the pin.

Refusing the variables is not enough on its own. With a mirror or binding URL
set, the `v8` build script writes the downloaded binding into the crate's
extracted source (`<registry>/src/…/v8-<version>/gen/`), and Cargo never
checks an extracted source again. A refused build, or any other build sharing
the cache, could leave the binding poisoned for the next build with nothing
set. So celld's build script also finds the `v8` package's source with
`cargo metadata` (crates.io's, without the pointer-compression or sandbox
features) and hashes `gen/src_binding_release_<target>.rs` against
`CELLD_V8_BINDING_SHA256`. That is the exact file the `v8` build script hands
rustc (`RUSTY_V8_SRC_BINDING_PATH`) when none of the refused variables is set.
On a mismatch the build fails, naming the file; deleting the extracted crate
directory makes Cargo extract it again from the checked `.crate`.

The order of the two build scripts does not matter:

- celld's build script runs before celld compiles. celld links the `v8` crate,
  so no binary is produced unless the check passed.
- With none of the refused variables set, the `v8` build script writes the
  binding only when the file is missing. celld's check fails on a missing
  file, or, if the download finished first, hashes what was downloaded. So
  nothing in the same build changes the binding after a passing check.
- When the binding changes between builds, Cargo recompiles the `v8` crate
  (rustc records the included file), and celld's build script runs again
  (it declares the file with `rerun-if-changed`), so the next build checks it
  before celld links.

What this does not cover is another process writing the extracted source
during a build; anyone who can do that can change any crate's source.

The archive cannot persist the same way. It is cached in the target directory
(`gn_out/obj/librusty_v8.a`), never in the extracted crate, and the `v8`
build script reuses it only when its recorded URL is the pinned one, its
recorded archive hash equals the pin, and the file still hashes to the
recorded value. Anything else is fetched and checked again.

`tools/v8/guard-test.sh` proves each case with real builds against a private
`CARGO_HOME`, including a poisoned binding after a refused build.

The archive is rusty_v8's own build (its release tag, its GN arguments,
Chromium's pinned clang and Rust) with one change: the `v8` submodule moves
from the release's V8 to the newest upstream patch on the same branch, with
Deno's V8 patches carried over, and the dependencies V8's `DEPS` pins move
with it. The Rust side of the crate is unchanged, and V8's public headers
must be the release's but for the patch level, so the crate's binding fits.

Each release's `BUILDINFO` records the inputs: the upstream tag and commit,
Deno's patches, the denoland branch whose tree the patched V8 equals, the
moved dependencies, the toolchain and the GN arguments.

Only `x86_64-unknown-linux-gnu` has an archive. celld's build fails closed
for any other target, naming it, rather than linking another V8; so
`release.yml` builds and ships x86_64 Linux and amd64 images only. A second
target needs its archive built on that platform and a per-target pin (the
`v8` build script takes one hash).

## Rebuilding when Chrome ships a V8 fix

One command rebuilds, checks, publishes and pins:

```sh
tools/v8/rusty-v8.sh update            # the newest patch on the pinned branch
tools/v8/rusty-v8.sh update 15.2.124.45
```

It runs these steps, each of which can also be run alone:

1. `build`: clone rusty_v8 at the tag `Cargo.lock` names (into
   `~/.cache/celld-v8`), carry Deno's V8 patches onto the upstream tag, follow
   V8's `DEPS`, build with `V8_FROM_SOURCE=1` at 16 jobs (`CELLD_V8_JOBS`) in
   rusty_v8's own checkout, outside celld's guard, gzip the archive and check
   the headers. About 15 minutes on 16 cores.
2. `verify-local`: build celld against the local archive and run its tests,
   with `cargo --config` overrides that leave the pin as it is;
   `celld --version` must report the new V8.
3. `publish`: upload the archive, the binding, `SHA256SUMS` and `BUILDINFO`
   as a release named `rusty_v8-v<crate>-v8-<V8>`, tagged at the current
   commit (push it first), then download it again and compare. A published
   archive is never replaced.
4. `pin`: download the archive from its public URL, check its hash, and only
   then write `.cargo/config.toml`.
5. `verify`: build celld against the pin and run its tests.

Then commit `.cargo/config.toml` and open a PR with the release's `BUILDINFO`.

`build` stops when a fix needs a person: a V8 version on another branch, a
moved `//build` revision (rusty_v8 patches it), public headers that changed
beyond the patch level, or a patched V8 tree that is not denoland's own
`<branch>-lkgr-denoland` (different patches, or a branch denoland has not
moved yet).

## Knowing when we are behind

`tools/v8/rusty-v8.sh check` names the newest V8 patch on our branch and the
V8 branches Chrome's stable and extended-stable channels ship. It exits 10
when a newer patch exists on our branch, and 11 when Chrome no longer
supports our branch. `.github/workflows/v8-check.yml` runs it daily and on
changes to the pin. GitHub runs scheduled workflows only from the default
branch.

## Version policy

Tracking patches on one branch only works while Chrome supports that branch.
Chrome now ships a new milestone about every two weeks (154 on 2026-09-22,
157 on 2026-11-03) and merges V8 fixes only to the stable and extended-stable
branches. V8 15.2's last fix landed on 2026-10-14 (15.2.124.45). By
2026-11-11, 41 fixes had landed on each of 15.6 and 15.7 that 15.2 will
never get.

So the policy is:

- Between `v8` crate releases, patch the crate's branch with `update`. This
  is cheap and mechanical.
- Move to the next `v8` crate release as soon as denoland publishes one. A
  new V8 branch needs rusty_v8's Rust bindings for it, and celld's own V8
  code follows those API changes. Rebuilding that ourselves is a rusty_v8
  roll (rebasing `denoland/chromium_build`, new build steps, binding
  changes), which is denoland's work and too much to carry in a fork.
- When our branch falls out of Chrome support before a crate release
  exists, `check` says so, and the gap is a known risk until the crate
  moves.

On 2026-11-11, rusty_v8 PR #2098 rolls to V8 15.8 (crate 158.0.0, CI
green, unreleased). 15.8 is Chrome 158's branch, so it will be supported
for a few weeks after release. Moving celld to it is the next V8 step.

## The V8 sandbox

The V8 sandbox (`v8_enable_sandbox`) confines V8's heap, so that a V8 memory
corruption bug, the usual kind of exploited V8 bug, can corrupt only memory
inside the sandbox. Escaping it needs a second bug. Chrome ships with it,
and Cloudflare runs Workers with it. celld builds without it, as Deno does.

Turning it on in celld would take:

- **A sandbox build.** rusty_v8 has a `v8_enable_sandbox` feature (it implies
  pointer compression) but publishes no archive for it, and its CI does not
  build it. Our build script would add a feature flag; we would be its first
  heavy user.
- **Copies instead of zero-copy buffers.** In the sandbox every `ArrayBuffer`
  backing store must be allocated inside it. rusty_v8 removes
  `new_backing_store_from_vec`, `_from_boxed_slice` and `_from_bytes`, which
  wrap Rust memory. celld uses `new_backing_store_from_vec` in three places
  (`js.rs` twice and `js/storage_ops.rs`). Each becomes an in-sandbox
  allocation and one copy.
- **A 4 GB heap ceiling per process.** rusty_v8's only sandbox configuration
  puts every isolate in one pointer-compression cage, so all the isolates in
  one celld process share 4 GB of V8 heap. Backing stores live in the
  sandbox, outside that 4 GB. celld gives every Durable Object its own
  isolate with a 128 MB default heap limit, so about 32 isolates at the
  limit fill the cage. Cloudflare avoids this with isolate groups, each with
  its own cage and sandbox. rusty_v8 152.2 has no isolate groups, and later
  versions build multi-cage only without the sandbox.
- **A terabyte of address space.** The sandbox reserves about 1 TB of
  virtual memory at startup. `LimitAS` must stay unlimited, as
  `contrib/systemd/fragment-celld.service` sets it.
- **External pointers.** V8 handles these through its external pointer
  table. Strings and `v8::External` values need no change in celld.

The cost is a few days: the feature flag and a sandbox archive, the three
copies, then measuring memory and throughput with many isolates. The 4 GB
ceiling is the real decision. It is acceptable for a single-organization
node, but it caps how many objects can be warm at once. Isolate groups with
a sandbox each would remove it, but that is a rusty_v8 change.
